# ADR 0003 – Event-Driven Core

| Field       | Value                       |
|-------------|-----------------------------|
| **Status**  | Accepted                    |
| **Date**    | 2025-01-01                  |
| **Deciders**| Engineering Team            |

---

## Context

VibePulse's primary value is **observing software evolution during AI-assisted development**. The platform must:

1. Ingest a high volume of events from developer machines (file changes, git operations, AI tool interactions).
2. Process and enrich events in near real-time.
3. Serve aggregated intelligence to the dashboard with low latency.
4. Support future analytical features (drift detection, health scoring) without requiring breaking changes to the ingestion layer.

### Core domain event types (initial)

| Event | Source | Description |
|-------|--------|-------------|
| `file.changed` | Daemon | A source file was modified |
| `file.added` | Daemon | A new file was created |
| `file.removed` | Daemon | A file was deleted |
| `git.commit` | Daemon | A commit was made |
| `git.branch` | Daemon | Branch was created/switched |
| `session.start` | Daemon | Coding session began |
| `session.end` | Daemon | Coding session ended |

### Options considered

**Option A – Direct REST writes (request/response)**
Each daemon event triggers an immediate HTTP POST to the API. Simple to implement but creates tight coupling: if the API is slow or unavailable, events are lost; high event volume creates API latency.

**Option B – Event-driven with message queue (chosen)**
The daemon publishes events to a message broker (Redis Streams in Sprint 1, optionally Kafka at scale). The API consumes from the stream asynchronously, enriches events, and writes to PostgreSQL. Dashboard subscribes to processed events via WebSocket.

**Option C – File-based buffering**
Daemon writes events to local files; API polls for new files. Simpler than a message queue but introduces file-system coupling, polling latency, and complex cleanup logic.

---

## Decision

Adopt an **event-driven architecture** as the core integration pattern between the Daemon and the API.

**Sprint 0**: No event processing implemented. Domain model and vocabulary established in this ADR.

**Sprint 1 implementation**:
- Daemon → publishes to **Redis Streams** (`XADD vibepulse:events *`)
- API consumer → **reads from Redis Streams** (`XREAD`), enriches, writes to PostgreSQL
- Dashboard → receives live updates via **WebSocket** (FastAPI + `asyncio.Queue` fan-out)

Redis Streams are chosen over a traditional message queue (RabbitMQ, Kafka) for Sprint 1 because:
- Redis is already in the stack (cache layer)
- Streams support consumer groups, acknowledgement, and replay — sufficient for initial scale
- Avoids introducing a fourth infrastructure dependency

---

## Event envelope

All events share a common envelope. Feature-specific payloads are carried in the `data` field.

```python
class DomainEvent(BaseModel):
    id: UUID              # generated by daemon
    type: str             # e.g. "file.changed"
    source: str           # daemon instance identifier
    timestamp: datetime   # when the event occurred (UTC)
    version: int = 1      # schema version for forward compatibility
    data: dict[str, Any]  # event-specific payload
    metadata: dict[str, Any] = {}  # extensible context
```

---

## Consequences

### Positive
- **Loose coupling**: Daemon does not depend on API availability; events are buffered in Redis during API downtime.
- **Replay**: Redis Streams retain events, enabling replaying missed events after a consumer restart.
- **Scale**: Consumer groups allow multiple API instances to share event processing load.
- **Extensibility**: New consumers (analytics workers, alerting) can subscribe to the stream without touching the daemon or existing consumers.

### Negative / Mitigations
- More moving parts than direct REST. Mitigation: Redis is already required; no new infrastructure in Sprint 1.
- Event schema evolution requires discipline. Mitigation: `version` field in the envelope; breaking changes increment the version and old consumers are kept until fully migrated.
- Harder to debug than synchronous calls. Mitigation: each event carries a correlation ID; structured logging includes event IDs throughout the processing pipeline.

---

## Future considerations

- Migrate from Redis Streams to **Apache Kafka** if event volume exceeds Redis capacity or if we need persistent log compaction.
- Introduce **CloudEvents** schema for interoperability with external observability systems.
- Add **dead letter queue** for events that fail processing after N retries.
